# Lab 9 - Gen AI Security with Local LLMs - Reflection

This lab was different from the earlier ones because the focus was on the behaviour and risks of large language models rather than on traditional network or system tools. Running models locally with Ollama made it feel more like working with any other service that could be part of an organisation's infrastructure, instead of a distant cloud API that I cannot see.

The prompt injection experiments were the simplest to carry out but they had a strong impact on how I think about Gen AI. It was surprising how easy it was to write a sentence that tried to override previous instructions and make the model reveal information about its setup. Even when the responses were not obviously dangerous, the test made it clear that user controlled text can strongly influence what the model does. For any real application that passes user input into an LLM, this means the prompt design and any extra safety checks around it are just as important as the model itself.

The session level data poisoning exercise showed a different kind of risk. By telling the model something false inside the conversation and then asking a related question afterwards, it was sometimes possible to steer the answer in the wrong direction. This did not change the model's permanent training data, but it demonstrated how quickly a model can adopt incorrect information inside a session. In a bigger system, if such outputs were stored, reused or taken as facts by other components, this kind of drift could cause real problems.

The model inversion style prompts made me think about privacy and sensitive data. When I asked the model about personal data or user profiles, it responded with generic but realistic sounding examples. This behaviour raises questions about how much can be inferred from a model's outputs, even when it is not directly leaking specific training records. It reinforced the idea that training data for large models needs to be chosen and handled carefully, and that users should be cautious about assuming that outputs are harmless just because they are "made up".

The model extraction part highlighted a more technical risk. By sending the same prompt several times and comparing the outputs, I could see how consistent or variable each model was. Highly consistent responses make it easier for someone to approximate the model's behaviour by collecting many input and output pairs. Even if they cannot copy the internal weights, they might still be able to build a cheaper model that acts similarly for common queries. This has implications for organisations that want to protect both their intellectual property and any custom tuning they apply to models.

Finally, comparing three different local models with the same prompts showed that there is no single, universal Gen AI security profile. Each model has its own style, level of detail and way of responding to injection attempts. This means that security reviews and testing need to be done on the exact model versions that will be used in production, not just on a generic example. It also suggests that changing the model behind an application is a significant security decision, not just a performance or accuracy tweak.

Overall, this lab helped me see LLMs as components that must go through the same kind of threat modelling and testing as any other part of a system. I now have a clearer picture of how prompt injection, session level poisoning, inversion style probing and extraction risks can appear in practice, and I am more cautious about how Gen AI features should be integrated into applications.
